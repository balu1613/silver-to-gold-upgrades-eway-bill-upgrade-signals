# Vyapar Silver → Gold Upgrade Analysis

**SQL (PostgreSQL) + Python + Power BI | Proof-of-work project for a Data Analyst role at Vyapar**

> **Data note:** This project uses a **synthetic dataset** I generated myself (Python, Faker + NumPy, seed 42), modelled on the plan structure of Vyapar's public pricing page. It is not Vyapar data, and findings describe this dataset only. This is an independent portfolio project, not affiliated with Vyapar.

## Business problem

Vyapar's Silver plan caps users at **10 e-way bills per month** (and 3 firms). Gold removes the e-way bill cap. Some Silver users upgrade, many don't, even when they appear to be outgrowing the plan.

I framed the analysis around three team-specific questions:

| Team | Question |
|---|---|
| **Product** | What does usage look like before an account upgrades? Is there an early-warning signal? |
| **Marketing** | Which verticals and city tiers convert most, so campaigns can be targeted? |
| **Sales** | Which current Silver accounts look closest to upgrading and are worth a call now? |

---

## Key findings

**1. Product: usage ramps up before an upgrade.**
Looking back from each upgrade date across all 78 upgraders, average usage as a share of the cap was:

| Months before upgrade | 4 | 3 | 2 | 1 |
|---|---|---|---|---|
| Avg % of e-way cap | 40% | 59% | 78% | 97% |
| Accounts in sample | 28 | 56 | 78 | 78 |

Four months out, upgraders look the same as non-upgraders (about 41% of cap). The climb through **60 to 80% of cap, 2 to 3 months before upgrade**, is the early-warning window. By 90%+ the upgrade is almost here, which is too late to call it early.

**2. Marketing: no segment converts reliably better.**
- Overall conversion: **15.6%** (78 of 500 accounts).
- By vertical: 6.5% to 21.7%. The highest and lowest rates come from the smallest groups (23 to 33 accounts), and Grocery and Pharmacy, the largest segments, sit almost exactly on the average (15.4% and 16.4%).
- By city tier: Tier 3 19.5%, Tier 2 14.5%, Tier 1 12.9%. A chi-square test gives p ≈ 0.24, so the gap is not statistically significant.
- Conclusion: **target by usage behaviour, not by vertical or city tier.** See the limitations below. The data was generated without a segment effect, so "no effect found here" does not mean "no effect exists".

**3. Sales: a rule-based call list of 48 Silver accounts.**
A Silver account is flagged when it is at **60%+ of cap in the latest month and in at least 2 of the last 3 months**. The list is bucketed by latest usage (call today / call this week / nudge) and sorted so the closest accounts come first. None of the accounts is at the cap yet (see limitations).

## Dataset

Generated by `data/generate_data.py` and loaded into PostgreSQL (`vyapar_db`).

| Table | Rows | Description |
|---|---|---|
| `accounts` | 500 | One row per business: vertical (10 types), city tier, signup date, plan tier, upgrade date, support tickets |
| `monthly_usage` | 3,000 | One row per account per month (Apr to Sep 2026): e-way bills used, `pct_of_eway_cap`, cap-hit flag |

**Cleaning (Pandas):** deduplication, negative-value fixes, city-tier casing, rebuilding the full account × month grid for missing months (flagged in `was_missing`), plus a validation pass on duplicate IDs, plan/upgrade-date consistency, impossible dates and cap violations.

## Approach and key SQL techniques

- **Months relative to upgrade, not calendar months.** Grouping by calendar month blurs the ramp, because accounts upgrade on different dates. I computed `months_before_upgrade` from each account's own upgrade date. (My first attempt grouped by calendar month and produced a false "rapid shift" signal. I caught this, explained it and fixed it.)
- **Pre-upgrade filter.** `month < date_trunc('month', upgrade_date)` keeps uncapped Gold usage out of the averages.
- **Conversion rates with a denominator.** `COUNT(*) FILTER (WHERE is_upgrader) / COUNT(*)` per segment, not raw upgrader counts, which only show which segments are large.
- **Lead scoring with CTEs.** A `latest` CTE anchors "now" to `MAX(month)` in the data. `FILTER` clauses compute the latest-month usage and the count of months at 60%+ in one pass.
- **Tenure is not ramp speed.** `days_to_upgrade` measures signup-to-upgrade time, so I did not use it to describe how fast usage climbs.

## Dashboard (Power BI)

One page: four KPI cards (total accounts, upgraded to Gold, conversion rate, Silver leads to call), the usage-ramp line chart (Product), conversion by vertical (Marketing), the lead table (Sales), and a one-line takeaway.

- Star schema: `accounts` and a `Calendar` table each connect one-to-many to `monthly_usage`. The lead table imports from a SQL query and relates to `accounts`.
- Measures are kept in a dedicated measures table. The `Months Before Upgrade` calculated column lives in `monthly_usage`.
- Palette follows Vyapar's brand colours: about 90% grey data with red used only for focus.

## Limitations (read before drawing conclusions)

1. **Synthetic data.** Real usage would be noisier. The ramp pattern here is built into the generator, so treat it as a demonstration of method, not evidence about Vyapar's customers.
2. **Segments have no built-in effect.** The generator gave every account the same upgrade probability regardless of vertical or city tier. Differences across segments are random variation on small samples.
3. **Firms count was unusable.** A bug in the generator capped `firms_count_that_month` at 3 for all accounts, including Gold. I excluded firms from the analysis for that reason and focused on e-way bill usage.
4. **Few "stuck at the cap" accounts.** Only 1 of 422 non-upgraders ever reached 10 bills, so there are no accounts at the cap in the Sales list.
5. **Retrospective, not predictive.** The 60% and 2-of-3-months rule is an analyst-chosen heuristic based on what upgraders looked like in hindsight. It has not been validated as a predictive model.
6. **Short window.** Six months of data means fewer accounts have 4 months of pre-upgrade history (28 at 4 months vs 78 at 1 month).

## What I would do with real data

- Validate the lead rule: test whether accounts flagged at 60% actually upgrade more often than unflagged accounts (precision and recall on a hold-out period).
- Retest segment conversion with larger samples before recommending targeting.
- Add feature adoption, plan-page visits and tenure as extra signals, then consider a simple logistic regression for upgrade probability.
- Schedule a refresh so the lead list stays current.

## How to reproduce

1. `python data/generate_data.py` to create the two CSVs.
2. Clean in Pandas, then load into PostgreSQL (`vyapar_db`) as `accounts` and `monthly_usage`.
3. Run `sql/analysis.sql`.
4. Open `dashboard/vyapar_dashboard.pbix` and point the data source at your local database.

Requires Python (pandas, numpy, faker, sqlalchemy, psycopg2), PostgreSQL and Power BI Desktop.
